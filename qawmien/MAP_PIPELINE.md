# The map pipeline — paint one screen, code the rest

The owner's process, written down so any map can be reworked on its own without
disturbing the world around it:

> "if we want to rework a specific map, we can just cut that and make it
> through codex. Like, example, position map [x,y] is wrong. We need to upgrade
> it, make it themed. We will give it that, and she will give us [it] themed.
> So when people enter, we will modify it with code. Easy and flexible."

That is the whole design. This file is how it works.

---

## The two halves, and why they are separate

| the PICTURE | the GRID |
|---|---|
| one painted image per screen | `block[][]`, `markers`, `neighbours` |
| generated by Codex, regenerable at will | authored by `tools/mkworld.py`, stable |
| decides how it LOOKS | decides where you may WALK |

**The picture never decides walkability.** That is why a map can be repainted
ten times without touching a line of game logic, and why "different code on
each block" holds: every cell carries its own state regardless of what is
painted over it.

## The template is what keeps them in step

Codex is not asked to invent a field. It is given the map's **blockout** — the
flat coloured-square rendering of that exact screen — and asked to paint it.

```
  green   walkable ground of this zone (grass / dirt / paving)
  dark    something solid stands here: rock, tree, wall
  blue    water, impassable
  ring    a BUILDING footprint — paint it in 3/4 so it reads solid,
          door on the side the ring shows a gap
  pale    road / paving
```

Because the art is painted **from** the collision grid, a painted rock lands
where `block[][]` already says a rock is. Registration stops being something to
get right and becomes something that cannot go wrong — the same reason gear
stopped drifting once it was stamped from measured anchors instead of drawn by
eye.

## Reworking ONE map without breaking its neighbours

This is the part that makes the process usable, and the part that can go wrong.

Adjacent screens **share their edge line**: the stride is 9, not 10, so the
last column of `field-2-3` and the first column of `field-3-3` are the same
strip of world. If a map is repainted alone and its edge changes, the seam
tears — you walk east and the ground jumps.

So a single-map regeneration hands Codex **three things**:

1. the map's own blockout, as the layout to paint;
2. the **edge strips of its four neighbours**, as context, with the instruction
   that the painting must continue those lines rather than start new ones;
3. the zone's theme (see `ZONES` in `tools/mkworld.py`).

and the result is checked at the seam before it is accepted.

### The gate

A repainted map is only installed if:

- its **edge pixels match** the neighbouring maps' edge pixels within tolerance
  — this is checkable and must be automated, exactly like `checkpose.py` gates
  sprite drift;
- `checkmaps` still passes: walkability, markers, links and reachability are
  untouched by definition, but prove it rather than assume it;
- the picture covers the screen with **no transparent margin**.

Art that fails the seam check is regenerated, not patched by hand. A hand-fixed
seam is a seam that breaks again the next time.

## The order of work, per map

```
1  mkworld.py        the layout exists in the data already
2  blockout.py       emit THIS map's template as an image
3  codex             paint the template  (+ neighbour edges as context)
4  seam check        edges agree with all four neighbours, or regenerate
5  install           the picture becomes that map's background
6  code on top       doors, entrances, NPCs, fights — markers on tiles the
                     picture already shows them on
```

Step 6 is deliberately last and deliberately easy. A door is a marker on a
tile; once the art and the grid agree, placing one is not an alignment problem.

## What this buys

- **Buildings can be 3D.** A tile atlas can only ever draw a building as tiles
  from a fixed set. A painted screen can show a tavern in real volume, which is
  the design win the owner is after.
- **A bad map is one regeneration away from a good one**, and the fix touches
  no code and no neighbour.
- **The world can be upgraded incrementally** — repaint the starting screens to
  a high standard first, leave the outer ones rougher, and improve them later
  without a migration.

## The risk, stated plainly

It is not yet proven that Codex will follow a blockout as a *layout* constraint.
It followed a base sprite sheet faithfully, but that was tracing a figure; this
is "put a rock exactly here". If it drifts, the fallback is a coarser contract:
let the picture carry **terrain and mood**, and keep small props as sprites
drawn on the grid, where they are already correct by construction.

That is why the first job is ONE map, proven end to end, before sixty-three.
